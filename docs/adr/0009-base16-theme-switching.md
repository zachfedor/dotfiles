# Base16 theme switching via a self-authored script, no external theming CLI

## Context

Issue 8 asked for consistent colorschemes across terminal and editor,
switchable with a single command. The repo is passthrough-first (ADR-0001):
hand-authored dotfiles are the source of truth, and Home Manager's job is
placement, not generation. Any theming mechanism has to respect that or it
undermines the whole model.

The first pass at this ADR standardized on **Flavours**, a Rust base16 CLI.
Building against it surfaced real problems: its own docs describe a scheme
schema (`system:`/`name:`/`palette:`) that the shipped 0.7.1 binary doesn't
actually accept (it wants a much older flat `scheme:`/`base00:`.. format);
its config directory is hardcoded per-OS with no override flag (macOS:
`~/Library/Preferences/flavours`, unreachable via `-c`/`-d`); and only after
fighting through both of those did a genuine "not maintained" picture emerge —
Flavours' own documented Nix companion repo is archived, open issues about
Emacs support and long-term stability go unanswered, and the maintainer
doesn't appear to use it in their own dotfiles. That combination — docs that
don't match behavior, plus a maintainer who has moved on — isn't something
worth building a daily-driver dependency on.

The requirements were also revisited directly with the user beyond the
original issue text: theme switching should support **open-ended sourcing**
(drop in any base16 scheme file, no curation gate — dropping "stuck with
base16" schemes chosen for you), **wallpaper-seeded palettes** (generate a
scheme from an image), and **OS-driven light/dark variant switching** (Nord
light ↔ Nord dark should follow the system appearance setting; switching
*base* theme, e.g. Nord → Gruvbox, stays a manual command). The last one is
explicitly nice-to-have, not required for this issue.

## Decision

Drop the external CLI entirely. The actual job — read 16 hex values out of a
scheme file, substitute them into three fixed output shapes — is genuinely
small once you're not also fighting an unfamiliar tool's path conventions and
undocumented behavior. `scripts/theme-switch` (Python; already a
`home.packages` dependency, stdlib only) does it directly:

- Reads `theme/schemes/<family>.yaml` or `<family>-<variant>.yaml` — the
  classic flat base16 format (`scheme:`, `author:`, `base00:`..`base0F:` as
  top-level keys), not the newer nested `system:`/`palette:` schema. No
  curation/vetting gate: any file that parses to 16 hex values works.
- Writes three generated **Adapter file**s directly (see **Domain terms**
  below for the concept): `~/.config/alacritty/colors.toml`,
  `~/.config/nvim/colors-current.lua`, `doom/themes/theme-colors.el`.
- Tracks the current **family**/**variant** in `~/.local/state/theme/current`
  (plain two-line text file) so `--variant dark|light` can reapply the current
  family in a different look without the caller needing to know which family
  is active.
- Best-effort pokes a running `emacsclient` to reload (`(zf/reload-base16-theme)`);
  no-ops silently if Emacs isn't running a server.

**Family vs. variant**: a family (`nord`, `solarized`, `gruvbox`) is a name
picked with a manual `theme-switch <family>`. A family with two looks ships
`<family>-dark.yaml` and `<family>-light.yaml`; a family with only one look
ships a bare `<family>.yaml`. `theme-switch <family>` keeps whatever variant
is currently active (falls back to `dark` on first run — no manual first-run
step, same guarantee the old Flavours activation hook gave); `theme-switch
--variant dark|light` reapplies the current family in the given variant. This
split exists specifically so an OS-appearance watcher (see Deferred) can drive
variant without touching family, matching "Nord light ↔ Nord dark should
follow the system, Nord → Gruvbox stays manual."

**Per-tool adapters** (unchanged shape from the original design, just
generated by our own script instead of a template engine):

- **Alacritty**: `alacritty.toml` (untouched) imports a generated
  `colors.toml` via `general.import`. Alacritty already file-watches and
  live-reloads, so this is free, instant reload. `alacritty/alacritty.toml`
  is placed as a *file-level* passthrough (`xdg.configFile."alacritty/alacritty.toml"`),
  not a directory-level one — `~/.config/alacritty` needs to be a real,
  writable directory so `theme-switch` can write `colors.toml` next to it; a
  directory-level `xdg.configFile."alacritty".source = ./alacritty` makes the
  whole directory a read-only nix-store symlink, which was a real bug caught
  in review before it ever reached a rebuild.
- **Neovim**: `programs.neovim`'s `initLua` (untouched) `pcall`s a generated
  `colors-current.lua`. This does NOT depend on `base16-vim` (or any
  pre-shipped neovim colorscheme plugin) — an earlier draft did, but
  base16-vim's runtime API for accepting arbitrary hex values at runtime
  couldn't be verified with the same confidence as the rest of this design,
  and repeating the "trust an unverified external API" mistake that sank
  Flavours wasn't worth it for a "not urgent" feature. Instead the generated
  file sets `vim.o.background` and calls `vim.api.nvim_set_hl` directly for a
  small, fixed set of ~20 core highlight groups (Normal, Comment, String,
  Function, diagnostics, diff, popup menu, ...) — less exhaustive than
  base16-vim's ~200 groups, but fully self-contained and easy to verify by
  reading the script.
- **Doom Emacs**: `config.el` (mostly untouched — `doom-color` calls become a
  thin `zf/base16-color` wrapper) loads a generated
  `doom/themes/theme-colors.el`. Doom's `doom-theme` switched from a Doom
  theme package (`doom-one`) to a generic base16 Emacs theme package
  (`base16-theme`, MELPA) so scheme switching doesn't need per-theme face
  overrides — base16's slot convention is fixed across every conformant
  scheme, so structure stays the same and only hues change. Concretely: the
  old `doom-gruvbox` special case in `config.el` (extra hand-tuned face
  overrides that no other Doom theme needed) is gone entirely, because
  base16-defined faces don't have that per-theme inconsistency.
  `base16-theme-define` (the package's generic "apply this 16-color plist to
  ~200 faces" function, confirmed directly against its source) takes an
  arbitrary name + plist — no scheme-name matching to get wrong, unlike
  base16-vim's per-scheme files.

**Reload strategy**: manual reload via keybinding for now (`SPC t r` in Doom,
`<leader>tr` in Neovim; Alacritty needs no work, it's already live) plus the
best-effort `emacsclient` poke from `theme-switch` itself. File-watchers
(Emacs `file-notify`, Neovim autocmd) are deferred — avoids running and
maintaining a watcher process for a "not urgent" ricing task.

**Bootstrap**: default family/variant is `onedark`/`dark`, matching the
previous hardcoded look, so adopting this doesn't visually change anything
until actively switched. A `home.activation` hook runs
`scripts/theme-switch onedark` idempotently (invoking the nix-store `python3`
directly, not relying on `PATH` inside the activation script) so a fresh host
lands on the default reproducibly, with no manual first run.

**Scheme sourcing**: no curation/vetting gate — any base16 yaml dropped into
`theme/schemes/` works, matching "forget being stuck with base16 [curation]."
Shipped with 5 files as a starting set (not a fixed allowlist):
`onedark` (default), `gruvbox`, `nord`, and the `solarized-dark`/
`solarized-light` pair (chosen specifically to exercise the family/variant
split with real, well-known values). The old design's "vet for red/green
swaps before adding a scheme" caution still applies in spirit — a bad scheme
file will produce bad `ls`/git-status colors identically across every tool —
but that's now the same amount of care as editing any other dotfile in this
repo, not a formal gate.

## Considered and rejected

- **Flavours** (the original decision this ADR replaces) — abandoned for the
  reasons in Context: docs/behavior mismatch discovered while implementing,
  hardcoded non-overridable config-dir on macOS, and an unmaintained-looking
  upstream (archived companion repo, unaddressed Emacs/stability issues,
  maintainer not dogfooding it).
- **`tinty`** (tinted-theming's own manager, same org as `base16-vim`/
  `base16-theme`) — a plausible actively-maintained alternative, but once the
  actual generation logic turned out to be ~150 lines of straightforward
  Python, adding *any* external binary dependency (even a well-maintained
  one) for something this small stopped paying for itself.
- **Stylix** — declarative, first-class HM module, but templates configs
  itself; fights ADR-0001's passthrough model and the existing hand-tuned
  `alacritty.toml`/`config.el`.
- **`base16-vim` for the Neovim adapter** — rejected in favor of a
  self-written highlighter; see the Neovim bullet above.
- **A curated/vetted scheme allowlist** — rejected per the revisited
  requirements (open-ended sourcing is a stated want, not an oversight).

## Deferred (not built now)

- **OS-driven light/dark variant switching.** The family/variant split in
  `scripts/theme-switch` and its state file exist specifically to make this a
  small addition later (a watcher just needs to call
  `theme-switch --variant <dark|light>`), but the watcher itself isn't built:
  macOS has no clean push notification for appearance changes without a
  small compiled helper (would need a LaunchAgent polling `defaults read -g
  AppleInterfaceStyle`); NixOS/GNOME could watch the
  `org.freedesktop.portal.Settings` dbus signal properly. Explicitly a
  "nice to have" per the revisited requirements, not required for this issue.
- **Wallpaper-seeded palettes.** Generating a base16 scheme from an image is
  real color-quantization work; reusing an existing single-purpose tool
  (`wallust` was the candidate discussed) just for that generation step, with
  the output dropped into `theme/schemes/` and applied via the normal
  `theme-switch` path, is preferable to writing a quantizer from scratch —
  but not built in this pass.
- **File-watchers** (Emacs `file-notify`, Neovim autocmd) for automatic
  reload without a keybind press.
